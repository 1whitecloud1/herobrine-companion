# Herobrine Companion 的 KubeJS 整合包接口

适用于 Minecraft 1.20.1 Forge（KubeJS 2001）和 1.21.1 NeoForge（KubeJS 2101）。
KubeJS 与其他兼容均随单一本体提供，不再发布 Herobrine Companion Compat 附属。

## 放置位置和修改范围

把脚本放在 `kubejs/server_scripts/`，例如 `herobrine_content.js`。
执行 `/reload` 后重新应用；不要在 `client_scripts` 中修改服务端奖励或交易。

当前公开接口支持：

- 奖励：新增、删除、替换奖励，修改领取所需信任度和奖励物品。
- 交易：新增、删除、替换交易，修改输入/输出物品、最大使用次数、经验（信任提升）和价格倍率。
- `event.hero` 和 `event.getTrustLevel()` 可读取当前交易实体及信任度。

它不提供通用的战斗伤害、技能冷却等数值修改事件。这些配置应使用本体配置文件；
不要把 `Java.loadClass` 直接修改内部字段当作稳定的整合包 API。

## 奖励

```js
HerobrineCompanionEvents.registerRewards(event => {
  // 修改默认钻石奖励（ID 2），保留其他奖励。
  event.modify(2, reward => {
    reward.requiredTrust = 5
    reward.clearItems()
    reward.add('5x minecraft:emerald')
    reward.add(Item.of('minecraft:enchanted_book'))
  })

  event.remove(0)
  event.add(100, 10, 'minecraft:nether_star', '3x minecraft:diamond_block')
})
```

方法：

- `event.add(id, requiredTrust, ...items)`：同 ID 已存在时替换；否则新增。
- `event.remove(id)`：删除，ID 不存在时不执行操作。
- `event.removeAll()`：允许有意清空全部奖励，不会被 JEI 重置为默认值。
- `event.modify(id, callback)`：修改已有奖励；不存在的 ID 会报告脚本错误。
- `reward.requiredTrust = value` / `reward.setRequiredTrust(value)`。
- `reward.add(item)`、`reward.clearItems()`、`reward.remove(index)`。
- `reward.getItems()` 返回物品副本；修改返回值不会影响奖励定义。

奖励 ID 是存档中“是否领取”的标识，必须非负。发布整合包后不要复用已使用的 ID
来表示另一份奖励，否则旧存档的领取记录仍会对应这个 ID。
默认 ID 为 0–6；自定义奖励建议使用 100 以上的稳定 ID。

旧全局对象 `HeroRewards.add/remove` 仍可用，但仅限在 `registerRewards` 回调中调用。
推荐使用回调参数 `event`，不要在脚本顶层或任意运行时事件中直接改奖励。
每次资源重载都从默认奖励重新生成，所以反复 `/reload` 不会叠加重复物品。
奖励脚本失败时保留上一份成功发布的数据，并在 KubeJS/游戏日志中报告错误。

## 交易

```js
HerobrineCompanionEvents.registerTrades(event => {
  // 只保留整合包自定义交易。
  event.removeAll()
  event.add('5x minecraft:apple', 'minecraft:emerald')

  if (event.getTrustLevel() >= 20) {
    // 双输入；最大 12 次，经验/信任提升为 2，价格倍率 0.05。
    event.add('3x minecraft:emerald', 'minecraft:book',
              'minecraft:enchanted_book', 12, 2, 0.05)
  }
})
```

方法：

- `event.removeAll()`：清空交易。
- `event.remove(index)`：按当前列表索引删除，越界会报告脚本错误。
- `event.add(input, output)`：默认次数 10、经验 5、倍率 0.05。
- `event.add(input1, input2, output)`：双输入，使用相同默认数值。
- `event.add(input1, input2, output, maxUses, xp, priceMultiplier)`。
- 单输入的完整版调用可把第二输入写为 `null`。

`maxUses >= 1`，`xp >= 0`；价格倍率必须是有限的非负数，不接受 NaN/Infinity。
物品参数使用 KubeJS 原生转换，支持普通物品字符串、`Nx namespace:item` 和 `Item.of(...)`。
带附魔/自定义数据的物品应先通过对应 KubeJS 版本的 `Item.of(...)` 构造后传入。
1.20.1 保留输入 NBT；1.21.1 保留输入显式设置的数据组件条件。
没有第二输入应传 `null`，不要传空气物品或不存在的物品 ID。

回调在服务端为具体 Herobrine 生成交易时执行，而不是只在 `/reload` 时执行。
脚本可以读取实体状态，但不要对实体进行传送、生成等副作用操作：
服务器也会为 JEI 创建一个未加入世界、信任度为 100 的预览实体执行回调。
JEI 展示的是这个预览快照，不代表每个玩家/实体都满足其中交易的条件。

## 同步与重载

服务端在玩家加入和 `/reload` 时同步最终奖励定义及交易预览；客户端不需要再次运行
奖励脚本来重建列表。奖励界面与 JEI 使用同步的数据；脚本删除的条目会从展示中隐藏。
已有实体的交易缓存随重载失效，正在交易的玩家会收到刷新后的列表。
正常交易后的刷新会保留未改变交易的使用次数；`/reload` 则重新生成交易定义。

新增同步使用可选通道/载荷，不改动现有主通道编号。
新旧本体混用时，旧端不支持该同步就不会发送，不能保证旧客户端正确展示自定义奖励；
实际整合包仍应在服务端和客户端使用同一版本的 Herobrine Companion。

边界：最多 256 个奖励、每奖励最多 64 个物品条目、最多 256 个交易。
单个奖励物品条目的数量为 1–64；不堆叠物品的多个奖励允许放在同一条目。
交易物品数量还受物品自身最大堆叠数约束。
同步数据上限 1 MiB，包含完整 NBT/数据组件；超限会记录错误，不发送不完整数据。

## 验证命令

在各版本仓库根目录执行：

```bat
.\gradlew.bat verifyKubeJSIntegration
.\gradlew.bat verifyKubeJSContentCodec
.\gradlew.bat verifyKubeJSAbsent
.\gradlew.bat build
```

`verifyKubeJSIntegration` 使用隔离的脚本夹具执行生产方法，覆盖重载、回滚、物品副本、
非法参数与客户端隔离；它不是启动游戏的联机测试。

开发运行：1.20.1 默认加入 KubeJS；使用 -PwithKubeJS=false 可移除该直接运行依赖。
1.21.1 默认不加入 KubeJS；使用 -PwithKubeJS=true 加入固定的 2101.7.2-build.379。
其他开发测试模组仍可能通过传递依赖带入 KubeJS；隔离检查会过滤对应 JAR。
`verifyKubeJSContentCodec` 使用真实 Minecraft NBT 缓冲和替代物品/注册表夹具，验证生产
快照逻辑的传输及边界；不在普通 JVM 中启动加载器，也不等同于真实客户端联机验证。
